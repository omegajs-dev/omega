# OMEGA Manager (@omega.js/manager)

The package's own long-form reference is [packages/manager/README.md](../../packages/manager/README.md) — the wizard, the manage cycle, the services, and the CLI surface all live there.

Every verb is NAMED ([#229](https://github.com/Omega-JS-Stack/omega/issues/229)): `omega manage` is the whole service walk (the ONE name — no alias; `npm run manage` is the packaged form), `omega dev` boots the local stack (`npm start`), `omega deploy` publishes. A bare `omega` at a brand root prints help and runs nothing — it used to default into the walk, which meant an arg-less command quietly rewrote a brand.

`omega status` reports what a folder is to OMEGA and writes nothing. It names the state (`empty`, `unrelated`, `template`, `half-done`, `brand` or `legacy`), lists each gap, names the target the folder sits in (`inTarget`), and ends on the one next command; `--json` prints the report as one JSON object and nothing else on stdout. The gaps are `missing.files` (what the scaffold plan writes and the folder lacks, minus what the brand's git ignore rules match: a clone never carries the `.env` stubs), `missing.targets` (declared, with no folder), `missing.config` (what the loader refuses), `missing.install` (declared packages no `node_modules` holds), `missing.env` (the keys `missingEnvKeys(config, env, { verb: 'manage' })` returns, names only, each `{ key, service, optional }`) and `missing.tools` (the machine tools the brand's targets need and this machine lacks, names only, from devkit's `machine-tools.js`; the printed report lists them under `Machine tools`). These are the keys for going live: the printed report lists them under one line naming `npm run manage`, which asks for them. A key is `optional` when its service never gates a manage run (`gates: false` in `REQUIRES`: the operator-only services, payments, AI, publishing), and the report lists those on their own line, "optional, for later". A brand runs locally with no env key, so a missing key never makes it `half-done`, and neither does a missing machine tool (`npm start` skips the target that needs it); a `brand`'s next command is always `npm start`. A folder holding nothing but `.DS_Store` is `empty`. A config with a retired key, or the old `apps/` shape, is `legacy`, and its next command is `npx omega migrate`. The state function is `src/lib/brand-state.js`'s `brandState(cwd)`; the omega Claude plugin's `omega:init` skill reads its JSON. **It runs from anywhere**: a verb that needs no brand and that only the manager owns (`status`, `onboard`) runs the manager wherever it is typed, inside a target included ([devkit/index.md](../devkit/index.md)). Its verb row is `readOnly`, so the boot's freshness heal and preludes skip it, and its brand load passes `record: false`, so no machine registry line is written either.

The `omega:manager` router skill from the omega Claude plugin loads automatically in any project with `@omega.js/manager` (and inside `packages/manager` here); it points back at this map and the brand guide.

`omega pipeline` (the brand's live full-cycle test, detailed in that README) closes with the **verify sweep** ([#48](https://github.com/Omega-JS-Stack/omega/issues/48)): after the `--deploy=<targets>` legs run, `verify:site` / `verify:domain` / `verify:cloudflare` prove the launch surface answers from the outside, as scorecard rows judged exactly like deploy legs; `--verify` alone runs the sweep without deploying, and a dry run, a demo-* brand, or a brand with no cloud project records gated skips instead of touching the network. That is the one-command repo-to-live path (manage → deploy → verify) — the story lives in [deploys.md](../shared/deploys.md), the code in `src/lib/verify-live.js`.

**A brand NESTED in another repo deploys through the snapshot lane** ([#872](https://github.com/Omega-JS-Stack/omega/issues/872)): the brand folder is what the brand repo holds, so an `omega deploy` pushes that folder to the repo's `omega-deploy` branch, as a snapshot chained on that branch's tip, and dispatches the composed workflow there (a brand-root fan-out pushes it ONCE for the whole run and hands every target the sha, [#901](https://github.com/Omega-JS-Stack/omega/issues/901)). `brands/playground-omega` inside the omega monorepo is the live case, and `npx omega deploy --target=desktop` at `brands/playground-omega` is the whole of what used to be a rehearsal repo with a generator script of its own. Two settings make that run: the brand's source repo is public (its root `package.json` says so), which means the manage walk's `repo` service checks the org's runner group for it ([repo.md](repo.md)), and the desktop workflow fires on dispatch only. The lane matrix and the pack step: [deploys.md](../shared/deploys.md).

`omega dev` opens with a manage cycle before it spawns any app leg ([#44](https://github.com/Omega-JS-Stack/omega/issues/44)), so brand-level edits (the brandmark and its derived set, certs) are redistributed on every boot instead of going stale — what refreshes when is the redistribution contract in [local-dev.md](../shared/local-dev.md). That cycle is the BOOT LANE ([#228](https://github.com/Omega-JS-Stack/omega/issues/228)): `config.js`'s `BOOT_SERVICES` — workspace, assets, disperse — the local file work the legs consume, about a second, while cloud reconciliation and rebuilds wait for `npm run manage` (or `omega dev --full`, the whole walk). It is the DELIVERY lane, and a boot is one of its two triggers ([#678](https://github.com/Omega-JS-Stack/omega/issues/678)): a brand-root `omega deploy` runs the same list before it fans out, so a publish never ships inputs a manage run happened to be current on. Secrets ride no lane at all — the brand-root `.env` is the ONE file humans and the manager edit, and every verb composes its target's runtime env from the cascade by schema (a running backend restages when that file changes). It also runs non-interactive: steps needing a human skip into the run summary's ⚑ pending list with their `npm run manage -- --service=<name>` hint rather than holding the terminal, the full preflight walkthrough still names what setup owes, and the legs boot regardless — only real errors stop the boot. A picked target whose machine tools are missing (a Firebase backend without Java or the Firebase CLI) steps aside with the one line naming the tool and its install command, the rest boot, and the boot exits 1 only when no target is left; `omega manage` prints the same line under its target list and walks on, and the wizard prints it after the target pick.

**Every way the boot is stopped unwinds the legs** ([#629](https://github.com/Omega-JS-Stack/omega/issues/629)): Ctrl+C (SIGINT), a supervisor's stop (SIGTERM) and a CLOSED TERMINAL (SIGHUP) all reach the same `shutdown`, registered off the ONE list every OMEGA supervisor imports, `STOP_SIGNALS` in [@omega.js/devkit's src/stop-signals.js](../../packages/devkit/src/stop-signals.js). It has to be the whole list, not a subset: the legs are spawned DETACHED so the orchestrator's stop can reach each leg's own grandchildren, which also means a signal the orchestrator does not listen for kills it outright and leaves every leg (the backend's emulator tree among them) orphaned with its ports. A second stop while one is running is a force kill, and a leg that has not gone in 20s is escalated, so no way of stopping the loop can wedge it.

**A write DELETES what the config no longer derives** ([#636](https://github.com/Omega-JS-Stack/omega/issues/636), Ian 2026-08-29): every generated output is derived from schema + config, so each write/disperse op that can enumerate its FULL expected set derives it, diffs against disk inside its OWN output boundary, and removes the strays after a successful write. Deleting a config key is a real removal, not a key that stops being read: drop `targets.extension` and the composed `.github/workflows/extension-*.yml` files a previous manage wrote are gone on the next walk. Human-authored files are NEVER touched: the reconcile is per-op and never a runner-wide sweep, it stays inside machine-owned output (the gitignored `.omega/assets/`), and in a dir that mixes the two: the brand root's `.github/workflows/`: a file goes only past a double lock, the GENERATED header AND the composed naming. What is deliberately NOT reconciled: a whole `targets/<dir>` on a key drop (it holds human app code), `.omega/certificates/**` (enumerable only with Apple API state, not from schema + config), a target's certs dir (its dests are documented HUMAN drop points an operator `cp`s into, so [disperse](disperse.md) reports a missing REQUIRED source as an error and still never deletes), and values inside human-mixed files: root/target `package.json`, `AGENTS.md`, `.claude/settings.json` stay heal-only, which is why disabling translation still leaves the SDK dep ([#168](https://github.com/Omega-JS-Stack/omega/issues/168)). The two surfaces are the [assets](assets.md) and [workspace](workspace.md) service docs.

**One walk FINISHES the job** ([#662](https://github.com/Omega-JS-Stack/omega/issues/662)): a service writes what it can, then WAITS on the external condition its own step still needs — a provider validating, DNS propagating, an async provisioning releasing — and completes that step in the SAME walk. The ONE mechanism is `pollWithSpinner` (`@omega.js/devkit/flows`): ENTER checks now, `s` skips, and a run with no TTY polls quietly or steps aside; `openBrowserAndPoll` is the same wait with a browser step in front of it, for a condition a human has to go and create. Every wait is gated on `canPrompt` (a dry run and a headless run never hold the terminal), bounded where the condition can go stale, and a wait that is skipped or runs out returns `status: 'warned'` with its `reason`, so the summary names what is still owed. "Set it and rerun" is not an outcome a service picks for itself — later runs are for CHANGES, not for finishing. The waits in the tree today: the edge service holds `emailurl.<domain>` grey until SendGrid validates the branded link and then proxies it in the same pass ([#646](https://github.com/Omega-JS-Stack/omega/issues/646)), the domain service waits for Cloudflare to assign a brand-new zone's nameservers before writing them at the registrar, the analytics service waits out GA's hold on a link it just deleted, and campaigns/cloud/search/edge wait on DNS propagation and zone activation the same way. Only a condition no wait can reach stays a rerun: a multi-day human review (AdSense approval), a value only a person can supply, a portal step with no API behind it.

A brand still carrying `apps/` instead of `targets/` ([#443](https://github.com/Omega-JS-Stack/omega/issues/443)) is not healed inside a run — nothing here carries standing backwards-compat machinery (Ian, 2026-08-21). Discovery FAILS LOUD on the old shape (`src/lib/brand.js`: the old shape is not a brand with zero targets, and walking it as empty would quietly do the wrong thing in every service) and names the one-time fix: `npx omega manage --migration=targets-rename --execute`, then `npm install`. That is a registered migration like any other (`src/services/migrations/ensure/targets-rename.js`) — an audit until `--execute`, moving the folder and flipping the root `workspaces` glob together, idempotent, and refusing a brand that carries BOTH folders rather than guessing which copy is real. It is the one migration a walk can never reach on the brand it fixes, so `runManage` runs it ALONE, ahead of the load that would throw. The consumer-facing row is in [breaking-changes.md](../shared/breaking-changes.md#one-vocabulary--a-brands-surfaces-live-in-targets-443).

`omega migrate` at a brand root is the OTHER direction of the same idea, and the ONE verb that converts a legacy brand to OMEGA ([#612](https://github.com/Omega-JS-Stack/omega/issues/612), [#885](https://github.com/Omega-JS-Stack/omega/issues/885)). It REPORTS by default and writes nothing; `--execute` converts. Its rule set is the ONLY code that knows an old name ([#859](https://github.com/Omega-JS-Stack/omega/issues/859)): the retired config table `src/migrate/retired-keys.js` and the retired `.env` table `src/migrate/retired-env.js`, both the manager's own, while the loader knows only the present shape and fails an undeclared key naming this verb ([config.md](../shared/config.md) § Validation). The run has four parts, in order:

- **Every authored omega file.** The same files the loader validates, one block each: the brand's `config/omega.json5` and each `config/omega.<environment>.json5` overlay beside it, the brand root's `config/seo.json5` sidecar (a target's own is never read; a loader file like the base: the loader reads its root as the `seo` section and judges it the same way, so its paths print from `seo.`), then each framework target's own `targets/<name>/config/omega.json5` and its overlays (a target's file is judged as that target's layer). Every retired key is deleted in place. The list is `src/migrate/retired-keys.js` (both halves: renamed NAMES and retired PATHS, the rows in [config.md](../shared/config.md) § Migration), matched against the file as WRITTEN rather than the merged view, so the path it prints is the line you would have deleted yourself. One line per key names the block that replaced it and why; the write goes through the comment-preserving editor (`removeConfigValues`: the key, its subtree and the comment documenting it go, every other byte stays). A row that carries a conversion MOVES its value instead, and refuses rather than overwrite a value already authored at the new path, or move a value it must not (a literal seo `author.token`, or a bare `env:` naming no variable: a `refused <path>: <why>` error line, the key left in place). Idempotent: a key that isn't there is skipped, so a converged brand's rerun leaves the file byte-identical. Moving the setting of a plain removal into its new home is still yours: the migrate removes the dead key, it does not guess the new value. Then the SAME pass judges what is left against the strict schema (config's `undeclaredAuthoredPaths()`, the one walk the web converter shares: the whole file, then each framework target entry hoisted the way its own load sees it): every path no row covers is a by-hand `due` line (`config.<path> is not a key the schema declares; remove it by hand`). Under `--execute` it runs after converting, so the list is what the brand still owes, and any such line exits 1 in both modes. This pass is the ONE judge of the brand's omega files: a target leg reports its own files only. It runs BEFORE the target walk, so a leg's merge meets the root's current key names, and every brand root omega file a leg writes (the web leg's conversion) is judged again after the walk, its findings replacing the first judgment's.
- **Every `.env` the cascade reads.** The brand root's `.env` and each `.env.<environment>` overlay beside it, then each target's own, one block per file that exists (nothing outside the brand root and its targets is read or written), against `src/migrate/retired-env.js`. Every line names a KEY, never a value. An env-side rename (`OAUTH2_GOOGLE_CLIENT_ID` → `CONNECTIONS_GOOGLE_CLIENT_ID`) is renamed in place under `--execute` in either spelling dotenv reads (`KEY=value`, `KEY: value`) with the value's bytes untouched, and refused when the new name is already in the file or no line spells the key in a form the rename can find; a value that moved into config and a key retired outright stay `due` as by-hand steps.
- **Every target.** The walk runs each target's own framework migration IN-PROCESS, in the verb table's `TARGET_ORDER`, through the `./migrate` subpath every framework exposes (`resolveTargetMigrate` in `src/lib/framework-bin.js`, the same mechanism the deploy fan-out uses for `./ensure-target`). Every leg answers one shape, `migrateTarget(targetDir, { execute, brandRoot, name })` (`name` is the target's folder name) returning `{ due, changed, errors }`: web converts a UJM site into the brand root's `config/omega.json5`, never a file of its own, and leaves a target's own `config/omega.json5` (its override layer) untouched ([web/index.md](../web/index.md), [#970](https://github.com/Omega-JS-Stack/omega/issues/970)), the backend reports bare requires the flat BEM install answered, the extension moves flat hook files into the nested layout, and desktop has nothing to convert yet. `--target=<a,b>` narrows the walk (the config pass always runs); a custom target steps aside with its line.
- **The config load.** Once every file is in its final state, the brand config is loaded the way a build loads it: the brand root through `loadBrand` (`src/lib/brand.js`, the manage walk's own load), then `@omega.js/config`'s `loadConfig` for each framework target. Every error the loader throws or returns (a secret-shaped key, a wrong type, a missing `type`) is an `error` line in a final `config load` block, a message a second load repeats printing once, so a config the build refuses never reports clean. A still-legacy config's report shows both its `due` lines and the load errors they cause.

The report prints one block per target, each line labelled `due`, `changed` or `error`, then a count, and ENDS on one line naming `docs/shared/breaking-changes.md` inside the installed manager ([#888](https://github.com/Omega-JS-Stack/omega/issues/888)): a shape OMEGA changes after a brand converted is never a migrate step, it is a by-hand entry in that register. A report exits 1 while anything is due or refused; `--execute` exits 1 on a refusal, while a key the strict schema refuses is still in a file, or while the loader refuses the brand config (a by-hand step left due otherwise never fails it). Inside a target folder the verb refuses and prints the root form, like every verb. The framework CLIs carry no `migrate` of their own; the backend's run-alone conversions `migrate:rules` and `migrate:markers` stay framework verbs, reached with `--target=`.

Both verbs are STEPS inside a bigger process, and that process has its own doc: [migration.md](migration.md), the per-brand playbook for taking a legacy brand (UJM/BEM/EM/BXM/WM) onto OMEGA ([#149](https://github.com/Omega-JS-Stack/omega/issues/149)). Six phases with checkable exit criteria — assessment against the register, config conversion, repo restructure, per-target migration, deploy and cutover, retirement — plus the trap register of silent-failure classes the first migration wave found. A run on a real brand is HARD GATED on Ian's explicit go, per brand.

`omega update` at a brand root fans the dependency update out over every target and ends on the root's own `@omega.js/manager` pin ([updates.md](../shared/updates.md#brand-root)). After its summary, a real install that moved that pin prints the by-hand block: each dated register entry due since the version the brand moved from (`<date>: <title>`, newest first), then the path of the register the install just put on disk, or the one line naming that file when the old version's publish day is unknown. The parse (`dueEntries`), the block (`formatDueSteps`) and `registerPath`, the one register path `omega migrate` also ends on, live in `src/lib/breaking-changes.js`.

`omega bump` at a brand root is the brand's ONE version writer ([#869](https://github.com/Omega-JS-Stack/omega/issues/869)). The brand root `package.json` `version` is the master and every `targets/<name>/package.json` follows it, so one verb moves them together:

| Verb | What it does |
|---|---|
| `omega bump` | Print `<brand.id> v<version>` and stop. Brand root only |
| `omega bump patch\|minor\|major` | Write the next number into the brand root, EVERY target (a target with no `version` gains one) and the brand lock's entries, one line per file. It never commits and never tags: the ship flow owns the `chore(release)` commit. Any other token is refused, naming the three kinds |

The rule lives in `@omega.js/devkit/brand-version`, shared so the writer and the gate cannot drift: every framework's `omega deploy` calls `assertBrandVersion` right after its target scaffold and BEFORE its secrets precheck, on every lane (`--direct` and `--dry-run` included, since the check is a read), and refuses a target whose number differs from the root's, naming the target and `omega bump`. The brand-root deploy fan-out inherits that refusal from the target verbs it spawns. The NAME is deliberate: `omega update` moves dependencies and `omega version` prints the installed omega. Not to be confused with the FAMILY lockstep check (`assertFamilyVersions`, [#794](https://github.com/Omega-JS-Stack/omega/issues/794)), which is about the @omega.js packages a brand installed rather than the brand's own release number.

## The setup contract — ask when needed, skip, or disable permanently

Every service that needs a credential or a one-time authorization behaves the SAME way ([#608](https://github.com/Omega-JS-Stack/omega/issues/608)). When a service runs and an input it needs is missing, it asks right then, through one helper (`src/lib/service-input.js`) and one gate (`confirmSetup`, the ONE home of that wording), with three outcomes:

- **Provide** — the Enter-gated open of the exact page that mints the value (ask permission, never auto-open), a masked paste, persisted to the brand `.env` and exported for THIS run, so a fresh brand configures itself mid-walk.
- **Skip for now** — this run steps aside; the next one asks again.
- **Disable permanently** — `<service>.enabled: false` lands in `config/omega.json5` (the tri-state opt-out) and nothing asks again until the line is deleted.

**The same rule reaches back to ONBOARDING** ([#770](https://github.com/Omega-JS-Stack/omega/issues/770)): a value the wizard cannot derive is a question it asks (the company, the GitHub owner), not a hole the first manage walk discovers. A resume run keeps the brand's existing values untouched.

**A needed value with no default is ASKED for, never warned about** ([#635](https://github.com/Omega-JS-Stack/omega/issues/635)). A service that finds a value missing opens the gate right then — env keys through `lib/service-input.js`, `config/omega.json5` values through `lib/config-flow.js`'s `resolveConfigValue` — and continues into the rest of its pass on what it just landed. "Set it and rerun" is not an outcome: a warn is what a run prints when nobody CAN be asked (headless), when the user stepped aside, or when there is no question to put (a Sentry token that sees zero orgs offers no choice).

**A default that is no answer is still asked.** Some keys reach a service already filled in the merged config: the manager's defaults give `domain` an empty registrar pick, an empty mailbox pick and an empty forwarding list, and the schema defaults `cloud.shared` to `false`. A caller tells `resolveConfigValue` what counts as answered with `present(value)`, so an empty pick or list is asked for. A caller that passes `present` also judges the path's own `false` with it, saying whether that `false` is the opt-out (the mailbox pick, the forwarding list) or an answer. Where only the brand's file can tell a default from an answer, `isAuthored(context, path)` is the check: it is true when the brand's own `config/omega.json5` holds the path, so `cloud.shared` is asked once and then never again. A run that cannot ask prints one dim line per ask instead and the service goes on as it does with the value missing: headless, `→ Set <path> in config/omega.json5, or run manage in a terminal to answer`; a dry run inside a terminal, `→ Set <path> in config/omega.json5, or run manage without --dry-run to answer`. The asks this brings to the walk: the registrar ([domain.md](domain.md)), the mailbox provider and the first forwarding rule ([edge.md](edge.md)), and the shared project ([cloud.md](cloud.md)).

**Non-interactive runs never prompt.** A CI run, a piped `omega dev` boot, or `--dry-run` prints a loud skip line naming the exact keys and where to mint them, and returns the machine-readable `missingEnv` list the run summary's 🔑 section aggregates. Values are never printed — names, labels, and mint URLs only.

**The run summary NAMES what warned** ([#643](https://github.com/Omega-JS-Stack/omega/issues/643)): the service runner records every warned or failed operation as `{ operation, reason }` on the service result, so the per-brand breakdown prints one `<operation>: <reason>` line per operation instead of a service-wide "some operations had issues". The reason is the operation's own one-liner — names and counts only, never values — and an operation that returns none is still named.

WHICH keys a service asks for, and WHEN, is the env schema's to say (`@omega.js/config`: each key's `askedWhen`, one rule per asking service, and the format table for the ship keys). ONE function answers it, `missingEnvKeys(config, env, { verb: 'manage' })` ([config.md](../shared/config.md) § The env schema), and both halves call it: `lib/preflight.js` checks the whole enabled set up front and prints one consolidated fix walkthrough, and the helper asks for whatever is still missing at the moment of need. A brand with no backend target is never asked for a key only the backend reads, and a brand on a `demo-` project is never asked for the cloud service's keys. Each fix line names the `.env` the key BELONGS in ([#910](https://github.com/Omega-JS-Stack/omega/issues/910)): a brand of a company is sent to that company's `company/.env` by path, the tier every sibling brand inherits, with the brand `.env` as the override; a standalone brand is sent to its own. A service marked `gates: false` takes only OPTIONAL inputs (an operator-tier service account, the AI keys, the payment keys, the ship keys), and a key whose ask honours a narrower switch of its own (one payment provider, one pixel platform) is optional too: its absence never gates the service, and Disable turns off only that switch. Which keys OMEGA mints for itself and which a human acquires is the env schema's to say (`@omega.js/config`, [#581](https://github.com/Omega-JS-Stack/omega/issues/581)), and so is the HUMAN half of every ask ([#867](https://github.com/Omega-JS-Stack/omega/issues/867)): the `label` a gate opens with, the `url` Enter-to-open walks to, and the `hint` that says what to do on that page all live in the schema entry, with `serviceInputSpec` filling each input from it. `src/config.js`'s `REQUIRES` registry keeps only the manager's own fields per service (`why`, `label`, `disablePath`, `prompted`, `gates`, `scopes`): no key name and no "when". A second copy of a mint page here is how every desktop signing key and every extension store key ended up with one in NEITHER place. `test/service-input.test.js` sweeps the registry against the schema, so a credential the manager reads but never declares fails the suite, and so does a pasted key with no label, no mint page and no hint saying where it comes from. A declared key the schema marks `generated:` is never PASTED: nobody can produce it but OMEGA, so the helper mints it in place (`lib/env-secret.js`'s `mintGeneratedKey`, the same mint the workspace `env-keys` op uses) and it never appears in `missingEnv`, because the 🔑 section names what a human must go and get. When such a key is the only thing missing no gate opens at all, headless runs included, which is how a payment or marketing service running before the workspace service still has `OMEGA_WEBHOOK_KEY` to build its forwarder URL from. When a pasted key is missing beside it, the gate runs FIRST and the mint happens only past it, so "Disable permanently" never leaves a freshly minted secret behind. A dry run names what it would mint and writes nothing.

The ONE instance where OMEGA MINTS a credential instead of taking a paste is the analytics service's TikTok token ([#448](https://github.com/Omega-JS-Stack/omega/issues/448)) — the portal authorization the setup walks, and what it does and does not persist: [analytics.md](analytics.md).

## Onboarding

`omega onboard` writes a new brand, and a rerun inside a brand adds the targets it lacks. The default target is the website alone, and a brand may have none. The GitHub owner lands as `repo.owner`. A folder made from the [brand template](https://github.com/Omega-JS-Stack/brand-template) is a first run: one `npm start` installs, asks a short wizard, writes the brand and boots the dev stack. Every flag, default and printed line is in the [README](../../packages/manager/README.md#onboarding)'s Onboarding section.

## Custom targets

Besides the framework targets, a brand runs targets the framework does not own: a Render API, a worker, a script ([#603](https://github.com/Omega-JS-Stack/omega/issues/603)). `targets.<name>: { type: 'custom' }` declares one (a second custom target is a sibling KEY, [#886](https://github.com/Omega-JS-Stack/omega/issues/886)), and everything it can DO comes from its own `package.json` scripts: **`start`, `build`, `test`, `deploy`, `clean`**. The manager runs each verb through `npm run <verb>` when the script is present and skips it LOUDLY when it is absent: a verb that quietly did nothing is indistinguishable from one that worked. Nothing is inferred, defaulted, or synthesized: no script, no verb.

Discovery leaves `entry.target` NULL and sets `custom: true` (`src/lib/brand.js`), so the `filter((entry) => entry.target)` every framework service already applies skips custom targets by construction. Exactly ONE manage op reads the flag instead: the **workspace service**, which checks the declared dir exists and never counts it among the unmapped. No machine composes an `.env` file for it ([#678](https://github.com/Omega-JS-Stack/omega/issues/678)); it INHERITS the brand keys instead: `manage.js` loads the env chain into `process.env` before it spawns anything, so a custom target started by `omega dev`/`omega deploy` has them, while a standalone run inside the target dir does not (there is no `@omega.js/config` in there to walk the cascade). At the brand root, `omega dev` boots a custom target's `start` in the same terminal fan-out (only when that script exists), and `omega deploy` / `omega test` / `omega build` / `omega clean` run its `deploy` / `test` / `build` / `clean` BARE. The one predicate is `isFrameworkScript` in `resolveTargetRun`: a script that is exactly `omega <verb>` is the framework's own and hears the brand's flags and scope after `--` (deploy's `--snapshot`, `--direct`, `--platforms`; test's `--extended`, `--lane=`, scope words), and any other script, a custom target's or a custom-mode backend's, runs with no arguments, because it has no contract for them. `omega test` reads the same predicate to keep a scope or lane off such a script, and `omega deploy --dry-run` stops at the plan for it instead of running it. A scoped `omega test <framework:…>` never addresses one; a bare run does. The verb→run decision has one home, `src/lib/framework-bin.js`, and the verb's row picks the lane ([#985](https://github.com/Omega-JS-Stack/omega/issues/985)); below a root, the dispatcher runs a verb in place only in a TARGET of one of its owner frameworks (a brand target or a standalone project), never in framework source such as `packages/manager`, where every verb refuses with the monorepo-root form. A fan-out verb (`fanout: 'each'`) takes `resolveTargetRun`: every target, framework and custom alike, runs `npm run <verb>` in its dir. A single-target command (`fanout: 'none'`, the pass-through's `firestore:set`, `emulators`, `launch`, ...) takes `resolveTargetCommand`: the picked target's framework CLI, bin by path, with the argv as typed, and a custom target steps aside in one line (`<verb> is a <framework> command; <target> is custom`). It reads the verb's `dryRun` fact off its row in the ONE verb table (`@omega.js/devkit`'s `src/verbs.js`), and a framework target's verb scripts are the ones that table derives (`@omega.js/devkit/verb-scripts`), so every framework serves every fan-out verb it owns, extension's `omega build` included since [#81](https://github.com/Omega-JS-Stack/omega/issues/81). Its sibling `resolveTargetScaffold` ([#901](https://github.com/Omega-JS-Stack/omega/issues/901)) is the same decision for the SCAFFOLD the deploy fan-out runs in-process: a framework target resolves `@omega.js/<framework>/ensure-target` (the one subpath all four expose) from where the target declares the dependency, a custom target skips loudly, and a framework exposing no such entry is an error rather than a silent no-op.

`omega build` and `omega clean` are themselves brand-root fan-outs over EVERY target type ([#603](https://github.com/Omega-JS-Stack/omega/issues/603) addendum): one shared walk (`src/lib/verb-fanout.js`, the two command files are its callers) with the deploy fan-out's target discovery, `--target=` picker and dependency order (backend first, custom targets last); the selection and flag-forwarding helpers every fan-out shares live in `src/lib/target-selection.js`, which `commands/deploy.js` re-exports for its own readers. Targets are independent: neither verb publishes anything, so a failure never stops the walk and any failure exits 1. `--dry-run` is CONSUMED by the fan-out rather than forwarded (no framework's `build`/`clean` reads it, so a forwarded flag would really clean): every target prints the command it would have run and the walk executes nothing, framework and custom target alike. Config rules and the validator's errors: [config.md](../shared/config.md) § Custom targets.

## A backend in custom-server mode

A brand's backend can run as its own server instead of Cloud Functions — `targets.backend.projectType: 'custom'` ([#584](https://github.com/Omega-JS-Stack/omega/issues/584)), the same `@omega.js/backend` app listening on `PORT` for a container host (Render & co). It is still a FRAMEWORK target, not a custom target: discovery maps it to `backend` as always and hangs the mode on the entry as `projectType`. What changes is only which verbs its framework can serve, and there are exactly two.

- **`omega deploy` runs the brand's own script** through the one lane every target takes: `npm run deploy` in the target dir, run bare since it is not the framework's `omega deploy`, a loud skip when the script is absent, and `--dry-run` stopping at the plan. A Functions deploy REFUSES in custom mode, so the brand owns the script that would run it. `omega test` runs the framework's own `omega test`, which in this mode skips the emulator boot, the health check and the account setup and runs the discovered suites. `resolveTargetRun` (`src/lib/framework-bin.js`) is the one lane.
- **`omega dev` boots the server, not the emulator**: every target's leg is its own `npm run start`, and a custom-server backend's `start` is the brand's server command (the backend's own `omega dev` refuses in this mode). The backend keeps its place at the front of the default set: its API is what the website leg points at either way.
- **The workspace `scripts` op turns PER KEY instead of skipping the target** ([#689](https://github.com/Omega-JS-Stack/omega/issues/689)): it still syncs the standard scripts whose verbs work in this mode (`test`, and every derived verb script but `deploy` and `start`) and leaves the brand its own `start` and `deploy`: never written, never scaffolded. The backend names them in ONE place, `CUSTOM_OWNED_SCRIPTS` (derived from its `FIREBASE_ONLY_VERBS`), which the walk reads through `@omega.js/backend/ensure-target` (`resolveTargetCustomOwned`).
- **The testing service stops demanding a `firebase.json`** a custom backend has no reason to carry — the ONE Firebase-only check in that service, noted with the reason instead of failed. The staged `dist/` check still runs: a custom backend builds like any other.
- **Everything else is untouched**: the rest of the workspace service, the update service's install + build, the assets and cloud services. The mode changes the ARTIFACT, not whether the brand is on Firebase — `firebase-admin` still loads, so a custom server that reads Firestore or verifies an ID token keeps working, and the services keyed on `cloud` gate on the cloud config exactly as before.

The framework side of the mode — what each refused verb prints, and what stays identical — is [backend/index.md](../backend/index.md); the deploy story is [deploys.md](../shared/deploys.md).

Each brand-level verb tees its whole run to its OWN file, `<brandRoot>/logs/<verb>.log`: `manage`, `dev`, and since [#623](https://github.com/Omega-JS-Stack/omega/issues/623) `build`, `clean`, `deploy`, `update`, `test` and `pipeline`, truncated on each launch, ANSI-stripped, gitignored. They shared one file until [#231](https://github.com/Omega-JS-Stack/omega/issues/231), where booting the stack truncated the record of the last walk; the fan-outs wrote nothing at all until #623, so the walk's own verdict had to be stitched from the per-target logs. A fan-out log carries exactly that verdict (header, loud skips, summary) because a target spawned alone inherits the terminal, and the deploy fan-out's concurrent group is piped into the same file line by line behind `[<target>] ` ([#901](https://github.com/Omega-JS-Stack/omega/issues/901)), each target still writing its own log. Grep them instead of re-running a manage or restarting the dev stack. The mechanism and the full per-surface path table: [logging.md](../shared/logging.md); where every brand surface is authored versus generated: [brand.md](brand.md#the-placement-contract--where-a-thing-lives-and-what-refreshes-it).
